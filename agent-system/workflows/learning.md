# Learning From Failures

Use this workflow after a meaningful regression, repeated correction, or recurring
workflow failure. It improves this coding project; it does not create a separate
task system, memory service, or unattended self-modification loop.

## Preserve the case

Record the observed behavior, expected behavior, relevant revision and environment,
minimal reproduction or evidence, and impact. Keep private note contents and
secrets out of examples. Use the existing issue, plan, test, or handoff instead of
creating a new record when that surface already owns the case.

## Diagnose the owner

Distinguish a source/context gap, routing error, ambiguous requirement, product
defect, validation gap, or reporting mistake. Fix the layer that owns the failure.
More root instructions will not repair a missing test or a dependency defect.

Keep arithmetic, identity checks, file transformations, and objective validation
deterministic where practical. Use model judgment for interpretation and choices
that cannot be expressed as reliable rules.

## Make the smallest reusable improvement

1. Preserve the accepted correction and rationale.
2. Add or update a meaningful acceptance/regression scenario when applicable.
3. Propose or implement the in-scope code, workflow, or reference change.
4. Replay the case and relevant adjacent failures; inspect the resulting diff.
5. Retain the result, limits, and rollback path in the existing record.

Adapt guidance within the current authorized task. Seek a decision for a new
product direction, changed authority, or consequential unresolved choice; routine
corrections and internal review are not new permission gates. Do not silently
promote an external post or an agent's suggestion into a shared rule.

Create a reusable skill only when the judgment actually recurs or a costly failure
warrants it. Include when to use it, when not to use it, owned inputs and outputs,
procedures, validation, and escalation. Keep the shared version here and provider
adapters thin. No new skill is required for a one-off fix.

## Evaluate imported advice

Treat an external source as a durable principle, workflow candidate, implementation
example, operational caution, or source-thin claim. These are evidence labels,
not adoption decisions. Check current owning docs and local fit before relying on
version-specific behavior. A local trial should have a representative case,
baseline, meaningful failure cases, bounded time/cost, and a visible outcome.

Do not import a vault's task semantics, personal content, tools, or deployment
rules just because its general practice is useful. The
[Zettelkasten source basis](../references/zettelkasten-practices.md) explains the
principles adapted here and their limits.
